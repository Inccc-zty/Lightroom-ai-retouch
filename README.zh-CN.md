# Lightroom AI Retouch

**中文** | [English](README.md)

> Skill 目录名：`lr-ai-retouch` · 仓库名：`Lightroom-ai-retouch`

让 AI 真正操作你的 Lightroom Classic —— 不是模拟鼠标拖滑块，而是直接读写 develop settings
和局部蒙版；每一次改动都导出验证。量化只做护栏，审美留给你。

```
原片 ──诊断──> 九步全局 ──> 分区蒙版 ──> 导出验证 ──> 定稿 + 原图对比
         ↑                      ↓
      六把刀                 差异图 / 高频比 / 缩略图测试
```

---

## 这是什么

**这是一个 AI Agent Skill。** 把整个目录放进你的 skills 目录
（`~/.workbuddy/skills/lr-ai-retouch`），agent 就能直接操作 Lightroom Classic。
如果你用的不是支持 skill 的工具，`references/` 也能当一套完整的后期方法论单独读。

一个仓库里有三样东西：

| | 是什么 | 在哪 |
| --- | --- | --- |
| **1. 一个 skill** | 入口：铁律、工作流、agent 调用的脚本 | `SKILL.md` + `scripts/` |
| **2. 一套方法论** | 诊断框架、九步、蒙版配方、40 条踩坑，不写代码也能读 | `references/` |
| **3. 一个 Lightroom 插件** | 让写入成为可能的 Lua 桥 | `assets/plugin/` |

## 两个最该先知道的能力

### 一、给它一篇网上的教程，它照着那个思路修

丢给它一篇文章、一段视频字幕、一份预设说明，或者只说一句
**「按网上那种修法来修这张」**，它会：

1. **按公式搜**——`<题材> + <具体难点> + post processing`，不搜「怎么修图」这种大词
2. **给来源分级**——只采纳被两篇以上独立来源同时提到的结论，单一来源只当参考
3. **把教程里的每个数字拆成两类**——**风格决策**（可迁移，如「高光压死让云有重量」）
   和**那张照片的解**（必须重算，如「曝光 −0.20」）
4. **按你的直方图重算**，然后才动第一个滑块

所以「修成教程里那种通透感」会变成一份具体方案，而不是套一个预设。
完整流程在 [`references/style-transfer.md`](references/style-transfer.md)。

### 二、先诊断，绝不把上一张的答案搬过来

每张图都先问同一个问题：**它本来靠什么分开？** 物理上只有六把刀，
不成立的那把，它不会硬造。

这不是空话。同一个动作——降背景饱和——救活了一张（绿蛇在苔藓上），
也毁了一张（草地里的杓兰）。三张照片从诊断到定稿的完整路径，
包括错在哪，都在 [`references/case-studies.md`](references/case-studies.md)。

## 它解决什么问题

### 最大的问题不是参数，是你拿回来的已经不是你的照片

把一张图丢进对话框，AI 在后台开盲盒，还你另一张图。那里面：细节被悄悄抹平、
该锐的地方被超分重画、**不该有的东西被编造出来**——它觉得那里该有一根草，就给你画一根。
你分不清哪一块是自己拍的、哪一块是它想的；想改一个地方，只能整张重来。

照片的第一价值是「这是我拍的」。这一条破了，后面所有的调整都是装饰。

**这个项目从头到尾不碰像素，只碰参数。** 你拿回来的是自己那张原片，
加上一组 Lightroom 的 develop settings 和蒙版。

| | 生成式 / 端到端 AI 修图 | 这个项目 |
| --- | --- | --- |
| 拿回来的是什么 | 一张新图片 | 你那张图 + 一组参数 |
| 像素 | 可能被抹平、超分、编造 | 一个字节都没动 |
| 修完还能继续调吗 | 只能整张重来 | 能，在 Lightroom 里手动接着调 |
| 能回滚吗 | 不能 | 一条命令回到零 |
| 能问「为什么是这个值」吗 | 不能 | 每层都有名字、依据和实测 |
| 能跟 AI 讨论吗 | 只能说「再好看点」 | 可以说「第 9 层太重，减半」 |

在这之下，才是常规 AI 修图的三个技术死穴：

1. **抄数值**。教程里的 `高光 −98、阴影 +71` 是别人片子上的解，换一张照片就是灾难。
2. **开环**。改完不知道有没有过头，只能靠「感觉」。
3. **审美量化**。用 RGB 均值判断「是不是太红」，结果把深绿树林判成死黑。

这个项目换了一条路：**在 Lightroom 里跑一个插件，用文件队列和外部进程通信**。
插件在自己的 Lua 解释器里执行，权限等同于你在界面上操作，所以：

- 能写小数点后 6 位的参数
- 能一次写十几层局部蒙版，每层几何精确到千分位
- 能读回全部 1000+ 个 develop 字段做验证
- 不受弹窗、焦点、分辨率、屏幕缩放影响

代价是慢（每步要导出验证）。但这个慢是必要的——**开环修图只会越修越偏**。

```
┌──────────────┐   写 <id>.cmd    ┌────────────────────┐
│ Python 客户端 │ ───────────────→ │                    │
│ lr_bridge.py │                  │  Lightroom         │
│              │ ←─────────────── │  AIBridge.lrplugin │
└──────────────┘   读 <id>.res    └────────────────────┘
        │                                   │
        ↓                                   ↓
   导出 JPEG                        读写 develop
   测量 / 判断                      settings + 蒙版
```

协议是纯文本 `key|type|value`，一行一个字段。没有端口、没有守护进程、
没有依赖库，只有文件读写。这也意味着它在 Windows / macOS 上行为一致。

### 蒙版是数据，不是画出来的

一个蒙版层就是一组数字：

```json
{"name": "主石顶光", "kind": "radial",
 "lt": [0.27, 0.66], "rb": [0.60, 0.83],
 "ev": 0.20, "clarity": 12, "texture": 8}
```

`ev` 是真实 EV，工具内部自动除 4.5 转成 `LocalExposure2012`。
坐标 0–1 归一化，原点左上。

### 相机配置文件可写

`CameraProfile` 长期被误认为只读。实测可写，值用纯名称：

```
Camera Flat / Camera Standard / Camera Neutral / Adobe Landscape / Adobe Standard
```

`Camera Flat` 是最平的配置（为最大后期空间设计），做成片怎么调都不通透。
换掉它往往比加十层蒙版更有效。

## 凭什么相信它修得好

这个 skill 不是"提示词合集"，它是从真实拍摄的 8000+ 张照片、几十次翻车里长出来的。
每一条规则后面都有实测数字，也都写清了它的**反例**：

| 规则 | 实测 | 反例（什么时候不能用） |
| --- | --- | --- |
| 主体和背景同色系时，降背景饱和 | 背景饱和 0.816 → 0.623，主体/背景色差 30.9 → 38.5 | 背景是画面主色时（花田里的绿），降饱和会让整张发灰——实测草地掉到 73，被判「压抑」 |
| 明度分离已经够强时什么都别加 | 亮度比 1.34 时再加 EV 只会产生打灯感 | 亮度比只有 1.02 时（旱獭与草地），必须改走色相 + 质感 |
| 压 HSL 某通道的亮度让它退后 | ✗ 错。压绿亮度 −7，草地饱和反而 0.36 → 0.42 | 因为饱和度按 `(max−min)/max` 算，分母变小比值升高 |
| 主体周围压一圈暗能让它突出 | ✗ 错。四面包一圈 = 剪贴画 | 正确做法是只在**背光方向**加投影，那是物体"落地"的唯一证据 |

**没有一条规则是通用的。** 所以这个 skill 的第 0 条铁律是「先诊断，再动手，
方案是这张图长出来的，不是上一张搬过来的」。

## 安装

### 前置

- Lightroom Classic（2018 年以后的版本都可以，开发与测试在 13.x）
- Python 3.9+
- Windows 或 macOS

### 三步

```bash
# 1. 放到 skills 目录
git clone https://github.com/Inccc-zty/Lightroom-ai-retouch.git \
        ~/.workbuddy/skills/lr-ai-retouch

# 2. 装 Lightroom 插件
#    把 assets/plugin/AIBridge.lrplugin 拷到 Lightroom 的模块目录，
#    或在 LR 里：文件 → 增效工具管理器 → 添加 → 选中该目录
#    Windows: %APPDATA%\Adobe\Lightroom\Modules\
#    macOS:   ~/Library/Application Support/Adobe/Lightroom/Modules/

# 3. 验证
cd ~/.workbuddy/skills/lr-ai-retouch
python scripts/lr_bridge.py ping
```

`ping` 返回 `{"running": true, "ok": true}` 就通了。
不通的话看 [`references/bridge-setup.md`](references/bridge-setup.md)，
里面按症状列了 6 种排查路径（心跳停了有不同原因，别一上来就重启 LR）。

### 队列目录

Python 端和插件端通过一个共享目录通信，解析顺序完全一致：

1. 环境变量 `LR_BRIDGE_ROOT`
2. `~/lr_bridge`（推荐）
3. `O:\lr_bridge`（兼容早期安装，仅当该目录已存在）

**两端必须指向同一目录**，否则命令会写进一个没人读的队列。
换机器时最省事的做法是设环境变量。

## 六十秒跑通

```bash
# 看当前选中的照片
python scripts/lr_bridge.py selection

# 读它现在的全部参数（1000+ 字段）
python scripts/lr_bridge.py dump --path "/path/to/photo.NEF" > before.json

# 改一个参数并等它落盘
python scripts/lr_bridge.py develop-set --path "/path/to/photo.NEF" --set Exposure2012=0.35

# 导出验证（带 AI 蒙版的照片必须用这个，它会自动处理弹框）
python scripts/export_shot.py --path "/path/to/photo.NEF" --dest ./out --long-edge 2400
```

**所有写操作都要显式带 `--path`。** 不带就写到"当前选中"，
你点一下鼠标就写错照片了——这是本项目最贵的一次事故。

## 核心工作流

### 第 0 步：诊断（不许跳过）

先问「这张图本来靠什么分开」。物理上只有六把刀：

| 刀 | 判据 | 放大它的手段 |
| --- | --- | --- |
| 明度 | 主体与背景亮度差 ≥ 15% | 提主体 / 压背景 / 核心阴影 |
| 色相 | 色轮上差 ≥ 45° | 让两侧朝相反方向走，不动色相本身 |
| 饱和度 | 一方明显更浓 | 降背景饱和（仅当背景不是主色） |
| 质感 | 主体有纹理、背景软 | clarity 给主体，负值给背景 |
| 焦点 | 景深已经把背景分开 | 后期只能靠 clarity 近似 |
| 空间 | 轮廓周围有留白 | **只能靠构图，本项目不改构图** |

**诊断数据必须来自参数全归零后的导出。** 带着旧调整的版本会给出相反结论：
实测同一张照片，主体/背景明度比在带旧调整时是 1.34（判「够了」），
归零后是 1.02（判「几乎没差」）——差 33 个百分点，方案完全不同。

### 第 1–9 步：全局九步

配置文件 → 曝光 → 白平衡 → 黑白场 → 高光阴影 → 对比曲线 → 色彩 → 蒙版 → 细节。

每步只动这一族参数，验完再进下一步，跨步绝不合并。
因为前一步会改变后一步的判断依据。

细节在 [`references/adjustment-order.md`](references/adjustment-order.md)。

### 第 8 步：分区蒙版

这是把「调过曝光」变成「有体积」的唯一手段。
经验值：**有明确光向的风景片，做完全局后至少还要 4–8 层光影，否则基本等于没做完**。

作用在主体上的效果**一律走布尔**（AI 主体 ∩ 几何框），纯几何框一定会把背景一起改了。
蒙版配方见 [`references/mask-selection.md`](references/mask-selection.md)、
[`references/light-sculpting.md`](references/light-sculpting.md)。

### 收尾：原图对比（强制）

```bash
python scripts/orig_compare.py --path "/path/to/photo.NEF" --out ./output --apply
```

一条命令完成：备份 → 参数归零 → 导出真正的原图 → 原样恢复 → 逐键校验（0 差异才算过）
→ 导出定稿 → 拼上下对比图。

**"原图"= 参数全归零后的渲染**，不许拿用户自己修过的版本冒充。
脚本内置三道保险：归零后层数一变立即回滚、逐键比对不过就报错、备份先落盘。

### 交接单——除了图，你还会拿到什么

在这个项目里，一张图本身不算交付。跟着图一起给你的还有：

- **完整全局参数表**：配置文件、曝光、白平衡、黑白场、高光阴影、对比、曲线、HSL、锐化
- **逐层清单**：层名、覆盖位置、关键参数，以及**这层在解决什么问题**
- **骨架层 vs 软层**：哪几层删了会塌，哪几层只是口味——后者你觉得重就直接减半，不用问我
- **备份路径 + 一行回滚命令**

这才让「讨论」成立：你可以说「第 9 层太重」，
也可以自己在 Lightroom 里点开那一层改掉，其他的一概不用重来。

## 用网上的教程做参考

这是本项目的核心能力之一。用户丢一个链接说「照这个风格修」时，
目标不是复刻参数，是复刻**决策**。

### 教程里的每个数字都要过一遍这张表

| 类型 | 例子 | 能否迁移 |
| --- | --- | --- |
| **风格决策** | 「高光压死，让云层有重量」 | 能，这是审美取向 |
| **风格决策** | 「紫、品红拉到底，清杂色」 | 能，这是手法 |
| **那张照片的解** | 「曝光 −0.20」 | 不能，取决于原片曝光 |
| **那张照片的解** | 「去朦胧 +17」 | 半能，取决于雾有多重 |

**迁移左列，右列必须按目标照片重算。**

### 自己搜的时候

关键词公式：`<题材> + <具体难点> + post processing`。
不搜「怎么修图」这种大词。有效与无效的例子、可信度分级、
「两个来源互相矛盾怎么办」，都在 [`references/style-transfer.md`](references/style-transfer.md)。

只采纳被**两篇以上独立来源**同时提到的结论——单一来源当参考不当规则。

## 能力边界（诚实版）

Lightroom SDK 不是万能的。这些是实测撞过的墙，写清楚免得你白试：

| 做不了 | 原因 | 替代方案 |
| --- | --- | --- |
| **亮度 / 颜色范围蒙版** | SDK 会把 `RangeMask*` 字段静默丢弃（试了 7 个键名 × 2 种蒙版） | HSL 分通道本身就是颜色范围选择 |
| **污点修复 / 内容识别填充** | 没有对应 API | 只能在 LR 界面手动点几下 |
| **画笔蒙版** | 没有对应 API | 用多个几何蒙版叠加近似 |
| **改构图** | 项目规则：不裁切、不旋转、不改比例 | 构图问题只写进报告，由你决定 |
| **AI 天空蒙版做大范围压暗** | 过曝天空上 alpha 实测只有 0.12，参数只生效一成 | 改用纯几何线性渐变 |

还有一个必须知道的坑：**写错键名时 Lightroom 不报错**。
`SharpenMask` 不存在（正确的是 `SharpenEdgeMasking`），写完返回 `applied: 762`，
读回来才发现没生效。所以**任何写入都要 dump 回读那个具体字段，不看 `ok`**。

## 常见问题

**Q：为什么不直接调 Adobe 的官方 API？**
没有这样的 API。Camera Raw 的 SDK 不开放 develop settings 的写入。

**Q：为什么每步都要导出？不能一次改完再看？**
因为前一步的结果会改变后一步的判断依据。一次改 20 个参数然后看图，
你无法知道是哪个参数造成的，也无法知道有没有过头。这是开环和闭环的区别。

**Q：能批量修一组照片吗？**
可以，但建议只批量套同一场景的同一套参数。
不同光线的照片必须重新诊断——这个项目里所有翻车都是"把上一张的解搬到下一张"。

**Q：为什么文档里有那么多"反例"和"我错了"？**
因为规则的价值不在于成立的时候，而在于知道它什么时候不成立。
每一条反例都是真实翻车记录，带实测数字。
